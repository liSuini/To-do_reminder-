# ADR-0002：标签存储为待办上的 JSON 列，不建独立标签表

- 状态：已接受
- 日期：2026-10-12

## 背景

待办支持多标签（如"工作""会议"）。经典关系建模是独立的 `tags` 表 + `todo_tags` 关联表（多对多）。本项目是单用户、单表核心、标签仅用于筛选展示的轻量应用。

## 决策

标签作为 `todos.tags` 列存储 JSON 数组（如 `["工作","会议"]`），不建独立标签表。

## 理由

- 系统唯一的标签操作是"筛选"与"展示"，无标签重命名、合并、删除等管理需求
- 单用户场景下标签数量级很小（<50 个），JSON LIKE 查询性能完全够用
- 少两张表 = 少两套 CRUD = 更少代码与测试面
- 标签列表（左侧栏）从现有待办动态派生（SELECT + 去重），无需预置

## 后果

**正面**
- 数据层最小化，模型只剩一张核心表
- 新建待办时输入即建标签，无"先建标签再挂标签"的两步操作

**负面 / 限制**
- 无法通过外键保证标签拼写一致性（"工作" vs "工作 "会产生两个标签）→ 通过前端从已有标签中选择 + 输入自动 strip 缓解
- 若未来要做标签管理（改名/合并），需要数据迁移 → 届时再补关联表，当前 YAGNI

**查询影响**
- 按标签筛选使用 SQLite 的 JSON1 扩展 `EXISTS (SELECT 1 FROM json_each(todos.tags) WHERE value = :tag)`，而非外键 JOIN

## 被否方案

- **tags + todo_tags 双表**：为不存在的管理需求付出建模成本
